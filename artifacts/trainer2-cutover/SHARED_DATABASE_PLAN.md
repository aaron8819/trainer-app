# Trainer2 on the existing V1 database: shared-database plan

Updated 2026-09-29 for shared-database preparation. This is a local implementation plan, not approval for a hosted change. Trainer2 is not deployed or admitted for real training; Phase 0 and the first usable release remain incomplete. The owner has declined a fresh production backup and restore rehearsal for this personal project; neither is a gate. Without a fresh backup, recovery from a database-level mistake is limited.

## Product and data decision

V1 and Trainer2 will eventually use the same existing Supabase PostgreSQL database. V1 retains its tables and workout history for reference. Reviewed additive migrations create the Trainer2 tables in that database. At an explicitly approved handoff, stop new V1 training writes for the one owner, create a fresh five-week Trainer2 block and enter starting loads manually. Do not import V1 workouts as Trainer2 execution history or require finishing the current V1 block. There is no permanent second database; a disposable representative V1 database is used for migration rehearsal.

Trainer2 has one owner. There is no Supabase Auth, signup, email-link login, multiuser account management, or issuer/subject binding requirement. The sole `Trainer2Owner` row binds to an operator-verified existing `User.id`; the expected ID is configured server-side as `TRAINER2_OWNER_USER_ID`. The FK, fixed singleton key, exactly-one-row lookup and ID comparison fail closed on absence or inconsistency. No email lookup or runtime account creation can establish ownership. Historical `Trainer2AccountPrincipal` rows are inert and must be explicitly reviewed before creating the new binding; the local provisioning helper refuses to reinterpret them.

An operator provisions a one-time setup verifier for that existing User. The owner sets a passcode in the local browser. The server stores only salted scrypt verifiers for setup and passcode, and a SHA-256 hash of each random device-session secret. A `__Host-` Secure, HttpOnly, SameSite=Lax cookie carries the opaque session ID and secret; the database validates every Trainer2 request and transaction-level authorization recheck. Each device has its own durable session, with 30-day sliding and 90-day absolute expiry. Sign-out revokes one session; Sign out every device advances the owner session epoch. Five wrong passcode attempts cause a 15-minute lock. POSTs require the configured exact Origin and reject cross-site Fetch Metadata. No passcode or token belongs in a URL, log, source file, or client-readable store. Local synthetic browser tests are not hosted security qualification.

## Ordered rehearsal and cutover

1. **Freeze and inspect source:** recheck the live production alias, Git source, V1 `User.id` privately, migration ledger/checksums, schema conflicts, PostgreSQL major version, grants, Preview credential scopes, backups, pending V1/device writes and write-pause state. Do not call V1 GET endpoints until inspected for effects.
2. **Prepare a disposable representative V1 database:** apply the checked-in V1 migration prefix to isolated PostgreSQL 17, create a synthetic V1 User, then apply the twelve additive Trainer2 migrations and restricted grants. Do not apply them to production under this task. Review any historical principal rows explicitly; never convert issuer/subject to the new binding automatically. Verify V1 definitions and synthetic User read/write behavior remain intact. See [the exact procedure](../../trainer-app/docs/architecture/trainer2/SHARED_DATABASE_MIGRATION_PROCEDURE.md).
3. **Qualify roles and transport:** resolve exact provider ACLs including `anon`/`authenticated` and PUBLIC grants on only new Trainer2 objects, the two provider views, session/direct connection transport, server role spelling and verified TLS/CA. Keep admin migration/provisioning credentials outside app runtime. Verify the identity runtime role cannot change the bound account ID or session secret, and training roles cannot read passcode verifiers or token hashes.
4. **Protect a future Preview:** under separate authorization, remove production DB/admin/owner credentials from both build and runtime Preview scope, configure exact build/runtime mode, write pause and deployment protection, then verify the immutable deployment ID. Direct V1 API/page probes must be denied before handler and connection; a mismatched artifact must return denial in both directions. The production alias must continue serving V1. Hosted single-user admission is still disabled until separately designed and reviewed.
5. **Synthetic shared-database qualification:** after separate exact approval, add only a named synthetic `User`, explicit singleton binding and restricted credentials; keep the real owner denied. Verify unauthorized direct requests, setup/sign-in, independent durable sessions, revocation, concurrency, plan creation/review/activation, logging/Skip/correction/finish/reload/next workout and phone layout. An approved hosted test must use synthetic rows only and an independently reviewed nonproduction admission path.
6. **Real training gate:** finish the blueprint's Phases 0–5, including offline continuation, corrections, restrictions, measurement and progression; inventory unsent device actions; choose the last V1 workout; authorize and provision the exact real `User.id`; create and review the new five-week plan with manual loads; establish one writer. Enable real Trainer2 access only through a separate account-scoped reviewed admission change and explicit go decision. Verify first saved log, reload/recovery, finish and next workout on a phone. Retain V1 history as read-only reference.
7. **Recovery:** before first Trainer2 write, V1 writing can resume after pending actions are checked. After Trainer2 workouts exist, preserve their rows, actions, corrections and local journals; prefer compatible roll-forward or a temporary admission pause. Without a fresh backup, recovery from a database-level mistake is limited. Never run both writers for this account or drop Trainer2 tables as automatic rollback.

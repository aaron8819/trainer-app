# Trainer2 on the existing V1 database: shared-database plan

Updated 2026-09-25 for the single-user decision. This is a local implementation plan, not approval for a hosted change. Trainer2 is not deployed or admitted for real training; Phase 0 and the first usable release remain incomplete.

## Product and data decision

V1 and Trainer2 will eventually use the same existing Supabase PostgreSQL database. V1 retains its tables and workout history for reference. Reviewed additive migrations create the Trainer2 tables in that database. At an explicitly approved handoff, stop new V1 training writes for the one owner, create a fresh five-week Trainer2 block and enter starting loads manually. Do not import V1 workouts as Trainer2 execution history or require finishing the current V1 block. There is no permanent second database; a disposable restored copy is only for migration and recovery rehearsal.

Trainer2 has one owner. There is no Supabase Auth, signup, email-link login, multiuser account management, or issuer/subject binding requirement. The sole `Trainer2Owner` row binds to an operator-verified existing `User.id`; the expected ID is configured server-side as `TRAINER2_OWNER_USER_ID`. The FK, fixed singleton key, exactly-one-row lookup and ID comparison fail closed on absence or inconsistency. No email lookup or runtime account creation can establish ownership. Historical `Trainer2AccountPrincipal` rows are inert and must be explicitly reviewed before creating the new binding; the local provisioning helper refuses to reinterpret them.

An operator provisions a one-time setup verifier for that existing User. The owner sets a passcode in the local browser. The server stores only salted scrypt verifiers for setup and passcode, and a SHA-256 hash of each random device-session secret. A `__Host-` Secure, HttpOnly, SameSite=Lax cookie carries the opaque session ID and secret; the database validates every Trainer2 request and transaction-level authorization recheck. Each device has its own durable session, with 30-day sliding and 90-day absolute expiry. Sign-out revokes one session; Sign out every device advances the owner session epoch. Five wrong passcode attempts cause a 15-minute lock. POSTs require the configured exact Origin and reject cross-site Fetch Metadata. No passcode or token belongs in a URL, log, source file, or client-readable store. Local synthetic browser tests are not hosted security qualification.

This plan supersedes that task and does not incorporate its Supabase Auth flow.
- Read-only hosting inspection on 2026-09-24 found that Preview inherited `DATABASE_URL`, `DIRECT_URL`, `DATABASE_SSL_NO_VERIFY` and `OWNER_EMAIL`; `TRAINER_WRITE_PAUSE` was Production-only. No Trainer2 production objects, restricted roles or migrations existed. These facts must be rechecked before any hosted action.
- The local code binds `TRAINER_BUILT_MODE` into the Next server artifact from the build's Preview intent. Preview runtime requires `TRAINER_DEPLOYMENT_MODE=preview`, rejects inherited V1 and Trainer2 database credentials and owner variables, and denies all V1 pages and APIs in the proxy before handlers. Both database composition roots reject Preview before constructing a pool. Either build/runtime mismatch fails closed. Ordinary V1 production builds retain their existing behavior with an absent mode variable. Preview auth and training remain disabled for hosted use; a safe local build is not permission to configure or deploy Preview.
- Trainer2 runtime still uses dedicated identity, read and write connections and PostgreSQL 17 effective-privilege checks. The identity role is now a restricted identity runtime role with only the owner/session column writes it needs. Trainer2 admission remains hard-disabled when local disposable mode is not explicitly enabled. The local browser flow is restricted to loopback development and synthetic data.
- V1 currently identifies its owner through `OWNER_EMAIL` and uses privileged `DATABASE_URL`. This legacy behavior remains unchanged in ordinary production. It cannot be reused as Trainer2 authentication. The candidate's hosted pooled URL, TLS and provider ACL issues remain unresolved: Supavisor username form differs from the strict role parser, strict TLS failed against the observed chain, two provider statistics views are PUBLIC-readable, and named browser-role grants can include TRUNCATE on new objects. Runtime credentials must not be privileged or inherited by a Preview.
- No production secret values or personal training rows were used in this local slice. Local browser/DB fixtures do not prove actual Vercel/Supabase transport, protected deployment configuration, or real account binding.

## Ordered rehearsal and cutover

1. **Freeze and inspect source:** recheck the live production alias, Git source, V1 `User.id` privately, migration ledger/checksums, schema conflicts, PostgreSQL major version, grants, Preview credential scopes, backups, pending V1/device writes and write-pause state. Do not call V1 GET endpoints until inspected for effects.
2. **Prepare a disposable restored copy:** authorize a fresh backup/export and prove restore to isolated PostgreSQL 17. Reconcile the candidate's additive migration chain and the local-only owner/session migration. Do not apply it to production under this task. Review any historical principal rows explicitly; never convert issuer/subject to the new binding automatically. Verify V1 data and behavior on the copy.
3. **Qualify roles and transport:** resolve exact provider ACLs including `anon`/`authenticated` and PUBLIC grants on only new Trainer2 objects, the two provider views, session/direct connection transport, server role spelling and verified TLS/CA. Keep admin migration/provisioning credentials outside app runtime. Verify the identity runtime role cannot change the bound account ID or session secret, and training roles cannot read passcode verifiers or token hashes.
4. **Protect a future Preview:** under separate authorization, remove production DB/admin/owner credentials from both build and runtime Preview scope, configure exact build/runtime mode, write pause and deployment protection, then verify the immutable deployment ID. Direct V1 API/page probes must be denied before handler and connection; a mismatched artifact must return denial in both directions. The production alias must continue serving V1. Hosted single-user admission is still disabled until separately designed and reviewed.
5. **Synthetic shared-database qualification:** after restored-copy success and separate exact approval, add only a named synthetic `User`, explicit singleton binding and restricted credentials; keep the real owner denied. Verify unauthorized direct requests, setup/sign-in, independent durable sessions, revocation, concurrency, plan creation/review/activation, logging/Skip/correction/finish/reload/next workout and phone layout. An approved hosted test must use synthetic rows only and an independently reviewed nonproduction admission path.
6. **Real training gate:** finish the blueprint's Phases 0–5, including offline continuation, corrections, restrictions, measurement and progression; inventory unsent device actions; choose the last V1 workout; authorize and provision the exact real `User.id`; create and review the new five-week plan with manual loads; establish one writer. Enable real Trainer2 access only through a separate account-scoped reviewed admission change and explicit go decision. Verify first saved log, reload/recovery, finish and next workout on a phone. Retain V1 history as read-only reference.
7. **Recovery:** before first Trainer2 write, rollback can restore V1 writing after pending actions are checked. After Trainer2 workouts exist, preserve their rows, actions, corrections and local journals; prefer compatible roll-forward or a temporary admission pause. Restoring a pre-cutover database would lose those workouts without a reviewed replay plan. Never run both writers for this account or drop Trainer2 tables as automatic rollback.

## Next concrete step

Obtain focused independent acceptance of the local single-user access and Preview boundaries, then authorize a fresh backup and disposable restore rehearsal. That rehearsal must reconcile migrations, the verified V1 `User.id`, historical principal rows and provider ACLs before any production migration or hosted Preview configuration. None of those hosted actions is authorized by this plan.

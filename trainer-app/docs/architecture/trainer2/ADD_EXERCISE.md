# Session-added exercises

Execution & Evidence owns `src/lib/api/trainer2/add-exercise.ts`. `AddExercise` uses the existing account-first durable command lock, authorization, origin and write-pause boundaries. The command names an owned execution and START content hash, a qualified catalog ID, working-set count (1–20), rep range, target RIR and optional measurement. Only the existing qualified catalog is accepted; the 59 exclusions remain unchanged. Catalog facts and recording semantics are captured at acceptance. Explicit exclusions remain instruction-owned.

`Trainer2ExerciseAddition` is an append-only, RLS-enabled execution fact. Its action, server time, policy, position ordinal, exercise snapshot, authored targets, canonical bytes and hash remain immutable. Positions and initial sets receive execution-owned UUIDs; they have no source-plan identity. Distinct actions may add the same exercise. Ordinals are allocated under the account lock and appended after START positions. Exact retries recover one accepted position/bundle even after closure; changed envelopes conflict. Finish binds all effective targets, so addition-first rejects a stale finish and finish-first rejects the addition. START, accepted programs, original targets and future workouts remain unchanged.

`execution-targets.ts` exposes base identities, immutable original positions and effective target identities for both origins. Added positions use their display identity and a null source position. Existing Add set, swap, result, skip, correction, finish, completed review and previous-performance consumers use this owner. Added-position swaps derive from the addition snapshot; Return to original restores its accepted exercise and authored targets. Any retained result revision or skip locks swapping, including cleared evidence. Results retain their exact assignment and measurements.

The shared qualified catalog picker appears below the exercise queue. Configuration defaults to two working sets, qualified rep defaults, the workout RIR and 120-second accessory rest. Weight is optional; bodyweight has no numeric weight field. Numeric targets preserve their qualified kind, convention, zero meaning and original kg/lb units (the picker authors pounds). Explicit load uses the existing two-decimal pounds display conversion rather than the five-pound suggestion policy; logging it unchanged retains the original measurement bytes. Editing the load records pounds. Otherwise the existing unambiguous compatible historical policy applies, including nearest-five-pound suggestions. Following sets copy nearest compatible recorded work within their position. Repeated historical matches abstain. Current duplicate occurrences never share preceding results.

Acceptance selects the first new set using the existing timer-aware reveal. Existing typed row inputs survive picker cancellation and acceptance. Addition neither starts nor resets rest; logging uses the existing timer owner. The queue distinguishes repeated occurrences and shows muscle labels there. Unresolved added targets require ordinary finish acknowledgement. No removal, reordering or subsequent target editing is included.

Pending exact envelopes are stored before delivery and recovered with the existing bounded request helper, including same-tab reload and closed-workout readback. Authoritative validated readback is required before publishing/selecting the new targets. Delayed reads cannot drop accepted exercise additions. Executions with exercise-addition facts are ineligible for empty discard.

## Migration and recovery

Apply forward migration `20261002010000_trainer2_add_exercise` after the released Add set migration, then the incremental Add exercise section of `prisma/trainer2-runtime-grants.sql`. Do not modify applied migrations or the reviewed swap checksum loader/matcher. The migration explicitly revokes PUBLIC and existing anon/authenticated/service_role privileges on every new table/helper. Restricted reader/runtime get SELECT, runtime gets INSERT, and both get EXECUTE on the two read helpers. Guard/seal functions have no direct runtime EXECUTE; no UPDATE/DELETE or SECURITY DEFINER access is added.

Deploy compatible readers and writers together after migration/grants under the established write-pause procedure. Once exercise-addition records exist, application rollback to a version without this read model is unsafe: it would omit durable positions, targets and finish bindings. Recovery must retain these facts and forward-compatible consumers; do not rebuild START, delete additions or promote them into prescriptions. Hosted changes require separate authorization.

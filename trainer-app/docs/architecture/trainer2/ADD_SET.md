# Session-added working sets

Execution & Evidence owns `src/lib/api/trainer2/add-set.ts`. Strict commands and immutable facts live in `src/lib/trainer2-contracts/add-set.ts`; `execution-targets.ts` and `exercise-swap.ts` under `src/lib/engine/trainer2` expose the current execution targets. START, accepted plans, original identities and future occurrences remain unchanged.

`POST /api/trainer2/executions/add-set` accepts `AddSet` with the existing action/device/account/ownership/dependency envelope. Its target names an owned execution and position; expected state binds START content hash and the reviewed exercise assignment; intent is empty. The account-first command lock allocates a new execution-owned UUID and the next position ordinal. Distinct actions on the same reviewed assignment can both append; they do not share a stale client ordinal. The position has a total limit of 100 sets. An Open workout may add before logging, after partial work, or after every existing set is logged/skipped. It needs an existing effective working target. Closed workouts reject new commands; exact retries still recover the historical accepted outcome. Changing any envelope byte under the same action ID conflicts.

Each immutable addition captures its action, server recording time, policy version, position, ordinal, target, exercise snapshot, reviewed assignment and canonical content/hash. It has no source-plan target ID. The new target copies the last effective working target's exact rep range, RIR, measurement and rest conventions; it is working and required for finish review. This is session intent, never performed evidence or a permanent prescription edit. Addition alone neither resolves work nor starts/resets rest. Log set uses the existing rest owner.

## Bounded swap extension

Untouched additions do not lock swapping. Every subsequent swap preview/hash includes all current targets, so an addition invalidates an earlier preview. Swap-first invalidates an addition bound to the old assignment. Any retained result revision or skip on an added set locks the entire position, including after clearing.

Original targets still derive from START. Added targets derive independently from their immutable addition capture, not a preceding substitution. Compatible purpose/rep basis retains the captured range; an incompatible replacement uses catalog defaults. Return to original uses original working rep defaults if incompatible. RIR/rest/classification/required status and identities remain captured. Numeric replacement load is blank. Return to original restores captured load only for additions originally captured on that same original exercise; additions captured on a replacement remain blank (or bodyweight where appropriate). These rules prevent accumulated target drift while retaining the addition's original facts. Saved substitutions and additions read back without today's catalog.

## Logger, finish and history

`AddSet.tsx` renders a compact chip after each position's set chips. It stores the exact pending envelope before delivery and uses bounded existing request recovery. Only authoritative validated readback selects/reveals the added target, using the active card's timer-aware scrolling. All existing row controllers and typed drafts remain intact. A conflict retains input and refreshes for a new deliberate action; uncertain delivery retains Check addition again across same-tab reload, including completed readback.

Actual suggestions use the nearest preceding recorded set in that position and assignment with the established compatibility barrier. Without preceding evidence, added sets use prescription or compatible historical load fallback. Suggestions are unsaved until Log set. Duplicate positions never share preceding results. Stored units, decimals and zero semantics are unchanged; display uses the existing pound conversion rules.

Queue counts, resolved progress, remaining work, finish input protection and reviewed finish bindings include every addition. An untouched addition requires the ordinary unrecorded-work acknowledgement. Explicit skips remain separate from performed work. Added targets use the existing log/skip/correct/clear/re-record and historical correction commands. Completed readback subtly labels them “Added during workout”; routine entry shows “Session target”. Older reads cannot drop an accepted addition or reinstall an older assignment. An execution with addition history is ineligible for empty discard.

## Persistence and verification

Forward migration `20261001010000_trainer2_add_set` adds append-only, RLS-enabled `Trainer2SetAddition` with account/execution/action foreign keys, globally unique added target IDs, unique position ordinals, content/hash checks, account-lock/source guards and deferred accepted-outcome sealing. It extends existing result/skip/swap/finish/discard membership and acceptance guards through execution read-model functions. It never updates START or historical rows. Domain measurement validation remains in the trusted server as in the existing swap/result guarantees; administrative trigger bypass is outside runtime guarantees.

The incremental section in `prisma/trainer2-runtime-grants.sql` explicitly revokes every table privilege and EXECUTE on all five new functions from PUBLIC and existing `anon`, `authenticated` and `service_role` roles before granting reader/runtime SELECT, runtime INSERT and EXECUTE on the three read helpers. The guard/seal trigger functions receive no direct runtime EXECUTE. This removes Supabase-style named-role defaults, including effective access by `service_role` with BYPASSRLS; RLS alone is insufficient. It grants no UPDATE/DELETE or SECURITY DEFINER capability. The connection privilege owner includes the new table. Hosted migration/grants and deployment require separate scope; this slice supplies local evidence only.

Focused credential-free tests extend the existing execution/swap/logger/finish/migration/route suites. `scripts/test-trainer2-add-set.ts --confirm-disposable` is registered as a task-owned synthetic PostgreSQL/browser command. It covers fresh/populated migration, restricted roles, direct invalid writes, exact replay, two-device additions, observed account-lock races in both orders, immutable originals, target meaning, actual prefill, retained input/timer, lost-response reload, restart and desktop/mobile completed readback. Only task-owned services are removed. Evidence and screenshots live locally under `artifacts/trainer2/add-set-evidence`; browser emulation is not a physical-device qualification.

The populated upgrade recreates broad table/function default privileges for all three API roles (including a BYPASSRLS service role), applies the unchanged forward migration followed by the incremental grant section, and proves effective denial of table access and execution of every helper using pinned role clients. It verifies PUBLIC ACL removal and successful restricted runtime addition/reader readback while preserving old START and results.

Teardown gives each resource a separate deadline and continues after rejection or timeout. Owned browser and Next process trees are captured and terminated explicitly, then protocol/client/pool cleanup runs, followed by bounded PostgreSQL removal and process survivor checks. A parent controller bounds the worker, observes its actual close, verifies the task-labeled container is absent, and removes the browser profile after the Windows driver releases its handles. Any failed/timed-out cleanup makes the runner exit nonzero. `report.json` separates assertions, cleanup, worker exit and actual runner exit; only the controller's exit publishes completed-run status. Cleanup regressions include stalled/failed/late-rejecting steps, failed/spawn-failed/stalled workers and a real owned child tree.

## Separately authorized release and recovery

1. Keep the write pause and protected synthetic admission in place. Review a clean correction commit/tree and complete required gates; record any failing full classification separately from diagnostic retries. Do not treat a targeted retry as a successful full run.
2. On an already provisioned Trainer2 environment, apply the unchanged forward migration `20261001010000_trainer2_add_set`, then execute only the section starting `-- Incremental Add set grants` in one administrative transaction. Do not rerun earlier role creation/policies. Fresh environments apply the complete migration chain then the complete grants file once. Never rewrite a previously applied migration.
3. If the old incremental section was already applied, the policies exist: execute only the new PUBLIC/named-role revocation block (through its `END $$;`) in a transaction; retain existing restricted grants and policies. Recheck effective table privileges and all five function ACLs for API roles/PUBLIC, restricted-role SELECT/INSERT and the three read-helper privileges. Do not solve this by changing provider-wide defaults or relying on RLS.
4. Deploy the reviewed compatible application only after grants. Retain the addition table/facts/identities and their grants during recovery. A pre-Add-set application omits added targets from reads and finish bindings; it is not an admissible rollback with accepted additions. Recover to a reviewed Add-set-compatible build, or keep writes paused while preparing one. Do not delete additions or modify START/results to make an older build fit.
5. Verify the deployed version against the exact approved commit/tree, then run the separately authorized protected synthetic journey: deliberate addition/exact retry/lost response/reload/restart; log/skip/correct/clear; untouched swap/restore; stale finish rejection; completed history, counts, unsaved input and timer. Inspect effective hosted ACLs as well as restricted-role writes/readback. Preserve the pause and synthetic-only admission until independent release review approves the evidence. Real owner admission is a separate action.

Local PostgreSQL/Edge evidence does not prove hosted provider defaults, hosted role memberships or release behavior. No production migration/grants, deployment or real-owner admission is authorized by this document.

# Session-added working sets

Execution & Evidence owns `src/lib/api/trainer2/add-set.ts`. Strict commands and immutable facts live in `src/lib/trainer2-contracts/add-set.ts`; `execution-targets.ts` and `exercise-swap.ts` under `src/lib/engine/trainer2` expose the current execution targets. START, accepted plans, original identities and future occurrences remain unchanged.

`POST /api/trainer2/executions/add-set` accepts `AddSet` with the existing action/device/account/ownership/dependency envelope. Its target names an owned execution and position; expected state binds START content hash and the reviewed exercise assignment; intent is empty. The account-first command lock allocates a new execution-owned UUID and the next position ordinal. Distinct actions on the same reviewed assignment can both append; they do not share a stale client ordinal. The position has a total limit of 100 sets. An Open workout may add before logging, after partial work, or after every existing set is logged/skipped. It needs an existing effective working target. Closed workouts reject new commands; exact retries still recover the historical accepted outcome. Changing any envelope byte under the same action ID conflicts.

Each immutable addition captures its action, server recording time, policy version, position, ordinal, target, exercise snapshot, reviewed assignment and canonical content/hash. It has no source-plan target ID. The new target copies the last effective working target's exact rep range, RIR, measurement and rest conventions; it is working and required for finish review. This is session intent, never performed evidence or a permanent prescription edit. Addition alone neither resolves work nor starts/resets rest. Log set uses the existing rest owner.

## Bounded swap extension

Untouched additions do not lock swapping. Every subsequent swap preview/hash includes all current targets, so an addition invalidates an earlier preview. Swap-first invalidates an addition bound to the old assignment. Any retained result revision or skip on an added set locks the entire position, including after clearing.

Original targets still derive from START. Added targets derive independently from their immutable addition capture, not a preceding substitution. Compatible purpose/rep basis retains the captured range; an incompatible replacement uses catalog defaults. Return to original uses original working rep defaults if incompatible. RIR/rest/classification/required status and identities remain captured. Numeric replacement load is blank. Return to original restores captured load only for additions originally captured on that same original exercise; additions captured on a replacement remain blank (or bodyweight where appropriate). These rules prevent accumulated target drift while retaining the addition's original facts. Saved substitutions and additions read back without today's catalog.

## Logger, finish and history

`AddSet.tsx` renders a compact chip after each position's set chips. It stores the exact pending envelope before delivery and uses bounded existing request recovery. Only authoritative validated readback selects/reveals the added target, using the active card's timer-aware scrolling. All existing row controllers and typed drafts remain intact. A conflict retains input and refreshes for a new deliberate action; uncertain delivery retains Check addition again across same-tab reload, including completed readback.

Actual suggestions use the nearest preceding recorded set in that position and assignment with the established compatibility barrier. Without preceding evidence, added sets use prescription or compatible historical load fallback. Suggestions are unsaved until Log set. Duplicate positions never share preceding results. Stored units, decimals and zero semantics are unchanged; display uses the existing pound conversion rules.

Queue counts, resolved progress, remaining work, finish input protection and reviewed finish bindings include every addition. An untouched addition requires the ordinary unrecorded-work acknowledgement. Explicit skips remain separate from performed work. Added targets use the existing log/skip/correct/clear/re-record and historical correction commands. Completed readback subtly labels them “Added during workout”; routine entry shows “Session target”. Older reads cannot drop an accepted addition or reinstall an older assignment. An execution with addition history is ineligible for empty discard.

It extends existing result/skip/swap/finish/discard membership and acceptance guards through execution read-model functions. It never updates START or historical rows. Domain measurement validation remains in the trusted server as in the existing swap/result guarantees; administrative trigger bypass is outside runtime guarantees.

The incremental section in `prisma/trainer2-runtime-grants.sql` grants reader/runtime SELECT, runtime INSERT and execution read-function access. It grants no UPDATE/DELETE, browser/PUBLIC access or SECURITY DEFINER capability. The connection privilege owner includes the new table. Hosted migration/grants and deployment require separate scope; this slice supplies local evidence only.

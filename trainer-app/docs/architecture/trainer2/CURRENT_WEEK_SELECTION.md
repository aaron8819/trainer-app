# Current-week workout selection and Program review

Planning owns eligibility in `src/lib/engine/trainer2/occurrence-resolution.ts` and explicit advancement in `src/lib/api/trainer2/advance-week.ts`. A programmed week is a contiguous stage UUID run in immutable authored occurrence order. Recurring stage UUIDs and duplicate labels remain distinct runs. `Trainer2Plan.currentWeekIndex` identifies the current run. Finish and Skip resolve occurrences; neither advances that cursor nor completes the program. Discard leaves the occurrence unresolved. All saved occurrences count, including optional-only workouts.

After the final occurrence resolves, Training keeps the completed week visible. **Continue to next week** submits `AdvanceWeek`. On the final run, **Complete program** completes the plan and leaves that final run visible. The command requires every occurrence in the current run to be resolved and no account-wide Open execution. It binds `target.planId` and `expected: { planRevisionId, acceptedSequence, weekIndex, firstOccurrenceId }`, with the existing action/device/account/ownership-epoch/dependency envelope and empty intent. The account lock, immutable `Trainer2WeekAdvance` fact, unique `(planId, fromWeek)` key, guarded cursor/lifecycle update and deferred outcome seal commit together. Exact replay precedes lifecycle/current-week validation. A repeated action replays its outcome; a new action carrying stale bindings conflicts without advancing a later week.

ReadNext retains its recommendation within the persisted current week, adds `eligibleOccurrenceIds`, and exposes strict `week` metadata (index, first occurrence UUID, member UUIDs, ready and final). A resolved Active week has a null recommendation and an empty eligible list; future pending occurrences remain supported. Completed plans also have a null recommendation. The contract validates membership and resolution, and continues rejecting unknown keys. Optional new fields let the **new reader decode old responses**; the released strict reader rejects new fields. They do not establish older-reader/new-server compatibility.

Start accepts any exact eligible occurrence in the approved revision, capturing its unchanged prescription and source/owned identities through the existing START owner. Different-week, finished/skipped, foreign and stale requests fail without domain changes. Account locking, exact durable outcomes, one ordinary attempt per occurrence and the partial one-Open-per-account index remain. Any account-owned Open execution prevents another start. Replay precedes current eligibility checks and never revives a discarded/finished attempt. The explicit Skip command uses the same current-week eligibility and rejects any account-wide Open execution; its conservative accepted-sequence/revision binding and exact pending recovery remain.

`TrainingOverview` presents all current-week workouts as Pending, In progress, Completed or Skipped. `Workout` initially selects the recommendation. An explicit selection changes only local UI state; preview and Start are separate. The start/skip envelopes bind that selected UUID. With an Open workout, Resume is offered and Start is absent. Completed results link to their saved execution; skipped prescriptions and provenance remain reviewable. Program has keyboard-operable week buttons, one visible week, single-column phone cards and two desktop columns. Exercise variation details use native disclosure. Controls have 44px minimum height. Focus stays on deliberate selection/navigation controls. The V1-style active logger, additions, swaps, history, prefill and Finish result binding retain their existing owners. Confirmed Finish returns home and starts nothing.

Reload loads authoritative state while retaining exact pending Start/Skip/AdvanceWeek commands. An uncertain Continue offers Check continue again; Start/Skip stay locked until the original outcome and authoritative readback are confirmed. Returning focus to Training/Program refreshes current state unless command/review delivery is locked. Read generations and accepted-sequence comparison reject delayed older reads. An uncertain start keeps Check again and does not substitute the current selection into its saved envelope. SessionStorage remains the existing browser durability boundary; device loss/full offline synchronization are outside this slice.

## Migration and recovery

Forward migration `20261004010000_trainer2_current_week_selection` adds the invoker helper `trainer2_current_week_eligible(text,uuid,jsonb,text)` and replaces only Start/Skip eligibility guards. Exact-source, identity, account, immutable prescription and deferred outcome guards remain. Historical migration bytes and Prisma model shape are unchanged. PUBLIC and existing provider roles lose helper access; only the restricted writer needs EXECUTE. The complete local grants file includes that permission. Incremental preparation, if separately authorized in a future environment, is:

```sql
GRANT EXECUTE ON FUNCTION trainer2_current_week_eligible(text,uuid,jsonb,text) TO trainer2_draft_runtime;
```

The follow-on forward migration `20261004020000_trainer2_explicit_week_advance` adds the cursor and append-only advancement table, replaces only the completion policy in the existing Finish/Skip guards, and seals explicit cursor/terminal changes. Existing source, identity, instruction, result, account and outcome guards remain. It initializes Active/Completed/Paused plans once from the released first-unresolved derivation (the final authored run if none remain). Already-progressed plans stay in their existing week; Completed plans stay Completed. No old Finish/Skip fact, result, START, action/outcome, session or immutable revision is rewritten. The migration adds state; it does not invent historical Continue actions. The prior activation guard is temporarily disabled only inside the atomic bootstrap; existing deferred activation seals are evaluated before re-enabling it.

For fresh installations, run the migration chain and the full `prisma/trainer2-runtime-grants.sql` preparation once. For populated upgrades, apply both current-week migrations, the eligibility helper grant above, and `prisma/trainer2-week-advance-grants.sql` once. The incremental file adds restricted SELECT/INSERT, named RLS policies and writer-only EXECUTE on the invoker grouping helper. PUBLIC and provider roles (including direct grants from provider default privileges) receive no table/helper access. No reader or identity helper permission, SECURITY DEFINER, bypass, role membership or object ownership is introduced. Do not rerun the full fresh-role file or the policy-creating incremental file against already-prepared roles/policies. Repeated migration deployment is ledger-idempotent.

## Coordinated release and recovery

A bounded wire-compatible rollout is not practical for the released shell: removing `eligibleOccurrenceIds` and `week` still cannot express a resolved **Active** week awaiting Continue; the old strict reader requires null occurrence to mean Completed. Its UI also has no Continue command. Do not fabricate a pending occurrence, erase supported state or weaken strict schemas to accommodate it.

A future separately authorized release must hold Trainer2 admission during preparation, apply migrations and incremental grants, deploy the matching current reader/server together, then refresh stale tabs in the **same tab** before reopening admission. Verify old-client/new-server rejection, new-client readback and exact pending-command recovery before considering the switch qualified. New server responses and explicit advancement semantics require their current recovery consumers. A database-only rollback or an older first-only reader is not a recovery option.

Preserve sessionStorage and the existing command/draft keys. Start, Skip, Finish, result, swap and addition consumers retain exact envelopes; `AdvanceWeek` uses `trainer2-advance:<account>:<plan>`. Entered result forms remain under `trainer2-result:<account>:<execution>:<target>` (historical drafts use their existing historical key). Do not close the only tab, clear storage, reset sessions, replace pending action IDs or substitute a newly selected target. If browser storage is unavailable, keep the tab open and retain entered values/exact pending envelopes before refresh. Recover pending commands with Check again against the matching server, reload authoritative state, and make a new decision only after a terminal conflict/rejection. Old pending Start/Skip envelopes remain supported and bound; stale commands may conflict and must not be silently rebound.

This is local implementation evidence. No hosted trial, plan, result, session, profile, provider grant or production database was changed. The retained protected Add exercise release report is separate hosted evidence.

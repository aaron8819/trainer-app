# Local Skip Workout

Planning owns `SkipOccurrence` in `src/lib/api/trainer2/skip-occurrence.ts`. This is the bounded local next-unstarted-workout slice. V1 remains live, hosting paused, and Phase 0 incomplete. It follows blueprint sections 8, 9, 11 and 16, domain architecture sections 7.2 and 8.2, and the implementation plan's Skip Occurrence command contract. Broader paused-plan operations, arbitrary future skipping and Skip Ahead remain unimplemented.

## Eligibility and exact confirmation

Only the next unresolved occurrence in an account-owned, non-tombstoned **Active** plan can be skipped. Its current revision must equal its immutable activated revision. The exact occurrence must exist in that revision's saved order, have no retained Open/Finished execution, and have no prior skip. Empty Open attempts must first be explicitly discarded through the existing command. Discarded empty attempts and their audit records remain unchanged and do not prevent a fresh reviewed skip.

`POST /api/trainer2/occurrences/skip` accepts the version-1 action/device/originating-account/ownership-epoch/dependency envelope, exact `target.planId` and `target.occurrenceId`, empty `intent`, and strict `expected: { planRevisionId, acceptedSequence }`. The sequence is the canonical decimal string returned by ReadNext, not a JavaScript number. It is the account's accepted-command sequence. This deliberately conservative binding invalidates confirmation after **any** accepted account change, including a Start followed by Discard, instruction changes or unrelated evidence correction. Rejected commands do not advance it. There is no inferred target, typed reason or client-assigned skip time.

The trusted principal is reauthorized inside `acceptCommand` after its account-first lock. Revision/sequence mismatch returns `STALE_SKIP_BINDING`; resolved or out-of-order targets conflict; a live execution returns `ALREADY_STARTED`. Missing/malformed envelopes fail validation. Changed payload under an existing action ID collides. Infrastructure errors abort the whole transaction and require the same envelope retry.

## Meaning, ordering and endpoint

`Trainer2OccurrenceSkip` is an immutable Planning decision, keyed by stable occurrence ID. It preserves account actor, activated plan/revision, action ID, exact expected binding, database-assigned skip time, approved endpoint IDs, prior Active lifecycle and whether this skip caused completion. Same-account foreign keys and SQL membership checks bind provenance. There is no execution, performed set, zero result, completion evidence or prescription rewrite representing a skip.

Planning's `readOccurrenceResolution` joins Finished executions and explicit skip decisions; `unresolvedOccurrences` preserves saved array order. Start, ReadNext, Finish and Skip reuse this rule. The SQL equivalent `trainer2_occurrence_resolved` is shared by Start, Finish and Skip guards. Duplicate names, stage names, dates and template labels never identify or reorder occurrences. The existing system derives next position; there is no mutable plan-position pointer to update.

Every saved occurrence is an approved retained obligation. The accepted schema has optional **sets**, not optional occurrences. A workout containing only optional working sets remains an obligation that can be finished or skipped. All-finisher plans still fail the existing activation validity rule. A single or final unresolved occurrence completes the plan atomically when skipped. Finish also recognizes previous skips, so either command can complete a mixed plan. No automatic next start, wrapping, reopening or progression recalculation occurs.

Skip fact, mandatory plan completion, accepted sequence and durable outcome commit together. SQL guards independently check next eligibility and binding under the same account lock, prevent ordinary execution coexistence, seal completion to its causal fact and require an exact accepted outcome at commit. Shared lifecycle commands use the same lock: Start-first rejects Skip; Skip-first rejects stale Start. Skip against an Open execution cannot implicitly finish/discard it. If Discard commits first, the older Skip binding is stale and needs a new review.

Exact replay returns the original durable outcome before current-state checks, even after later start/finish or final plan completion. It does not advance again. Old Start/Discard replays remain historical and cannot revive a discarded attempt or rewind current selection. Finished results, later corrections and all earlier audit records remain unchanged.

## Readback and UI

ReadNext retains its no-store, repeatable-read/read-only boundary and adds `acceptedSequence` and ordered `occurrences` with Pending/Finished/Skipped resolution and immutable skip provenance. Open execution display still takes precedence. The current next ID must equal the first unresolved summary ID; Completed has no next. UI displays Finished as Completed while explicitly distinguishing Skipped and explaining that completed workouts may contain unrecorded sets.

`SkipWorkout` is a secondary action beside Start. It names the exact workout and stage, explains advancement, and explicitly explains final completion. Cancel writes nothing and restores focus. Confirmation keeps its original snapshot through refresh and disables confirmation if the target, revision, sequence or live-execution state changes. Start remains locked until retained Skip storage has been checked and while review or uncertain submission is pending. Account/plan-keyed recovery survives next-occurrence changes and reload through sessionStorage.

Before submission, the exact command is saved. Lost, malformed or mismatched responses retain **Check skip again** with identical bytes. A successful receipt must match action, target, revision and sequence; its historical completion flag does not supply present UI state. Success requires current validated ReadNext containing the exact skip action and consequence. Failed/mismatched readback retains recovery. Request generations ignore late reads; terminal/current state cannot be replaced by an older response. Plan cards update from authoritative completion readback. Skipped summaries have no Start or result-edit controls. The saved full prescription stays available in the plan.

## Migration, permissions and verification

One forward migration, `20260915030000_trainer2_skip_occurrence`, adds the immutable, RLS-enabled skip table, outcome/lifecycle seals, shared resolution predicate and narrow extensions to existing Start/Finish/plan/acceptance guards. Historical migrations are unchanged. Administrative role preparation adds four table grant/policy statements and runtime-only EXECUTE on the invoker resolution predicate. Reader is SELECT-only; runtime has SELECT/INSERT, with no UPDATE/DELETE/TRUNCATE on skip history. No PUBLIC grant, SECURITY DEFINER function, browser role, hosted admission or legacy writer is added. The accepted trusted server roles remain account-spanning; application principal predicates enforce user authority. Administrator DDL bypass is outside this contract.

The guarded launcher is `node node_modules/tsx/dist/cli.mjs scripts/test-trainer2-skip-workout.ts --confirm-disposable`. It uses synthetic accounts, task-owned PostgreSQL 17 and installed Edge through repository-local Playwright, checks populated accepted-base schema upgrade and redeploy, independent persisted-order assertions, observed PostgreSQL blocking queues, rollback, permissions, browser journeys and same-database application restart. The upgrade retains Active/Completed plans, performed history, historical corrections and discarded attempts without inventing skips; only test adapters supply absent skip reads while exercising base-compatible commands against the old schema. This is not an old-binary deployment qualification.

`SkipWorkout.test.tsx` covers confirmation/recovery and its actual Workout parent; `occurrence-resolution.test.ts` covers saved-order policy and strict bindings.

# Local workout finish and next occurrence

Execution & Evidence owns `FinishExecution` in `src/lib/api/trainer2/workout-finish.ts`. This implements the bounded local start, results, finish, readback and next-start journey. V1 remains live, hosting paused and Phase 0 incomplete. Blueprint sections 8,16-18,26 and domain architecture sections 7.3,8,9,13.3 ground its meaning.

## Command and unfinished work

`POST /api/trainer2/executions/finish` uses the existing version-1 action/device/account/ownership-epoch/dependency envelope and trusted principal. `target.executionId` selects the owned execution. `expected` contains its initial `contentHash` and every execution-owned `targetId`, `resultVersion` and `performedSetId`, sorted by target ID. Targets with explicit skip history additionally bind `skipActionId`; never-recorded targets bind zero/null; cleared results retain their positive version and performed identity. Equal-value corrections remain distinguishable newer versions. Missing/extra/stale bindings fail without completion.

Intent is `{ acknowledgeUnrecorded: boolean }`. Required, optional and cleared targets without current results require one explicit acknowledgement and remain unknown. Finish never fabricates results, zeros, omissions, skips or adjustments. Existing explicit skips remain distinct from untouched work in review and readback; both count as unperformed and require acknowledgement. Reasons and set-by-set cleanup are not required. Logging all sets alone never finishes. The confirmation shows unknown required/optional counts and explains that later correction preserves completion; its reviewed snapshot stays fixed across background refresh.

## Transaction and lifecycle

The shared acceptCommand owner locks Trainer2AccountTrainingState before reading domain state. Finish validates ownership, Open state, complete reviewed result versions and the unchanged Active source revision. It appends immutable Trainer2ExecutionFinish with the action, expected binding, unknown targets, timestamp, source, prior Active lifecycle, approved endpoint IDs and planCompleted consequence. It changes execution Open to Finished and, when all retained occurrences resolve, plan Active to Completed. Existing partial unique indexes release Open/current membership. The exact durable outcome seals atomically. Failure rolls back all effects. Finish never starts another workout.

Planning derives occurrence resolution from the linked execution's authoritative finish fact or an explicit [Skip Workout](SKIP_WORKOUT.md) decision; there is no separate editable resolved flag. All ongoing record/correct/clear/re-record commands share account-first locking. The SQL result guard rechecks Open and absence of a finish fact after the lock, preventing stale preflight and direct same-transaction append bypass. Result-first makes an older finish stale; finish-first prevents further ongoing mutations. Finish insert validates versions/unknowns against persisted rows. Lifecycle guards require a same-transaction finish, whose deferred seal requires the execution state, plan consequence and accepted outcome.

Exact envelope replay returns its durable receipt, even after final closure or later workouts. Changed payload under the same identity is an action collision. A distinct finish of a Finished execution returns ALREADY_FINISHED. Historical command success does not claim current plan state. The separate [historical result correction command](HISTORICAL_SET_CORRECTIONS.md) is implemented for existing recorded sets; Undo Finish remains future work. Ongoing result commands are not repurposed after completion. No broad offline synchronization or device-loss durability is claimed.

## Next selection and UI

ReadNext and the existing StartOccurrence command select the earliest unresolved UUID in immutable activated occurrence order. Names, stages and exercise labels cannot substitute for identity. Finished and explicitly skipped occurrences are ineligible; no wraparound occurs. An account-owned Open execution takes display precedence, including when viewing an older completed plan. Existing source, account and exclusion checks still govern Start.

The accepted schema has optional sets, not optional occurrences. Every saved occurrence is retained intent, including an optional-only workout. Optional unrecorded sets never block finish or resulting plan closure after acknowledgement. Resolving the last occurrence completes the plan even when partial. Completed returns null next occurrence and cannot start another workout. An activated template retains its supported fixed schedule; arbitrary template-plus-added-workout authoring is unsupported. Independent plans can mix copied prescriptions and manual workouts in saved order.

Execution GET retains the original capture, current saved results and finish record. Browser validation checks account/execution, initial hashes, finish versions and unknown target IDs. Next reads include explicit Active/Completed lifecycle and reject contradictory endpoint responses. Completed screens show original targets alongside saved results, followed by explicit Start workout or Plan complete/No next workout.

Finish is blocked while any result input is unready, unsaved or pending. Users explicitly save/discard/recover it; no auto-submit or discard occurs. Confirmation locks local result controls. Conflicts retain input and require a new explicit review/finish decision. Before submission the exact finish envelope is saved in account/execution-scoped sessionStorage. Lost/malformed responses retain Check finish again. Acceptance triggers authoritative completed readback; failed reads retain the original pending command. Keyed components ignore delayed responses from another execution. Existing result input remains recoverable if another device finishes. Bookmark reload and same-database process restart preserve completion and results.

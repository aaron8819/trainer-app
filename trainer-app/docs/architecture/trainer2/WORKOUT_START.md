# Local workout start and immutable prescription

Execution & Evidence owns the bounded `StartOccurrence` command in `src/lib/api/trainer2/execution.ts`. It uses the existing trusted principal, `acceptCommand` account lock and immutable outcome infrastructure. This extends local activation only. V1 remains live, hosting paused and Phase 0 incomplete.

`POST /api/trainer2/executions/start` accepts the established version-1 action/device/account/ownership-epoch/dependency envelope, `target.planId`, `target.occurrenceId`, `expected.planRevisionId`, `expected.instructionEpoch`, and empty `intent`. The browser never supplies an authoritative prescription. References are account scoped. Under the account lock the handler verifies Active lifecycle, exact approved/current revision, supported saved intent, exact source occurrence and current exclusions before writing.

Only the first occurrence in the immutable revision's authored occurrence order is eligible. The UUID identifies it; order selects it. Display names, stage ordering and template assumptions do not identify work. No finish/skip command exists, so start does not advance this selection, resolve an occurrence, change a plan, or create performed evidence. Later-occurrence requests explicitly fail without substitution.

One successful transaction inserts `Trainer2Execution` with lifecycle Open, fixed start instant, source plan/revision/occurrence/action, canonical full initial prescription and SHA-256; increments the accepted sequence and persists the durable command outcome. The version-1 START document contains VERIFIED_START provenance, `trainer2-start-v1`, the exact source content hash, stage and whole occurrence, unchanged ordered exercises and set targets, planned-prescription progression, current immutable instruction snapshot, and execution-owned position/target IDs with ordered source-ID links. The source occurrence contains prescription values once; the identity map contains no competing values. Repetition basis/ranges, decimal spelling, valid zero versus null load, load convention/unit, optional/classified work, effort, rest, exercise descriptions/catalog provenance and roles are retained.

The initial capture is embedded in the immutable execution root for this slice. The full graph is small and no adjustment head is needed yet. Future session adjustments and set assertions must use separate owned records; they cannot update this initial document. Historical migrations are unchanged. The additive migration enforces same-account foreign keys, one ordinary source link, a partial unique Open index, source and identity seals, canonical/hash agreement, immutable update/delete guards, and an exact accepted outcome. It extends the existing owner-specific acceptance validator while retaining Draft, activation, instruction and accepted-sequence checks.

Restricted server runtime gains SELECT/INSERT on the new table; the reader gains SELECT. Neither receives UPDATE/DELETE/DDL. RLS is enabled, PUBLIC receives no grants, and no browser role is admitted. The established threat model trusts the server's account predicates and domain validation; these server roles can see all accounts. Administrators can change DDL and are outside the runtime immutability guarantee. Hosted admission and Origin validation remain unchanged.

Exact envelope retries return the durable outcome before current-state checks: IDs, timestamp and prescription never regenerate. Altering an action envelope causes an action collision. A new command for the same started occurrence returns ALREADY_STARTED; an Open execution from another source returns OPEN_EXECUTION_CONFLICT. The account lock orders races, while database uniqueness backstops both restrictions. Infrastructure failures abort the entire transaction. Stale revision/instructions, foreign or missing source, ineligible later work and exclusions fail before domain writes.

`GET /api/trainer2/plans/[planId]/next` selects the next source and any account-owned Open execution. `GET /api/trainer2/executions/[executionId]` reads the stored capture only, checking strict schema, ownership, structural identity bindings and integrity. Both HTTP reads run repeatable-read/read-only transactions and return private no-store responses. Missing, corrupt or unsupported capture fails explicitly; no current plan/catalog reconstruction occurs. Reload and Continue are reads, not lifecycle commands.

The activated-plan card offers Start workout and a preview, or Continue workout. `/trainer2/dev/executions/[executionId]` is bookmarkable and shows the saved exercise/set prescription alongside the separately owned [performed set results](SET_RESULTS.md). Pending starts are retained as canonical commands in sessionStorage before submission. Repeated clicks are locked. Uncertain/malformed responses retain Check again; remount retries exactly. Account/subject-keyed components and request generations discard delayed results. Validated acceptance navigates to a separate authoritative read. Browser storage failure prevents submission.
